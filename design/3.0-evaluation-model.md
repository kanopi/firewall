# 3.0 evaluation model

**Status:** proposal. Nothing here is implemented in 2.x.
**Settles:** [#38](https://github.com/kanopi/firewall/issues/38).
**Unblocks:** [#224](https://github.com/kanopi/firewall/issues/224) (the migration tool),
[#221](https://github.com/kanopi/firewall/issues/221) (replay, which verifies a migration).
**Supersedes the description in:** [#74](https://github.com/kanopi/firewall/issues/74), which
describes three buckets. There are seven.

This document exists because #224 cannot be written without it. A tool that rewrites
somebody's weights to preserve their current outcomes needs today's model stated exactly,
tomorrow's model decided, and the transformation between them written down — and two of those
three were issue prose, one of it stale.

---

## 1. Today's model, as the code has it

Verified against `Firewall::evaluate()` and `PluginConfigNormalizer::partitionAndSort()` at
v2.27.0, not from documentation.

### 1.1 The prologue

Before any rule is consulted, in this order:

1. CLI bypass (`shouldBypassForCli()`)
2. `mode: disabled` — returns immediately
3. Challenge submission handling (consults the durable block list first)
4. Lockdown — `lockdown: true` and the address is not in `lockdown_allow`

None of this is rule evaluation, and none of it changes in 3.0. It is listed so the migration
tool does not have to rediscover it.

### 1.2 The buckets, in the order they are consulted

| # | Bucket | Terminal? | Notes |
|---|---|---|---|
| 1 | `allow` | yes — request is served | Beats everything below, including a durable ban |
| 2 | *the durable block list* | yes | Not a bucket. Consulted **after** allow (`Firewall.php:1460`) |
| 3 | `mark` | **no** | Annotates and continues |
| 4 | `record` | **no** | Writes to the block list and continues; refuses nothing now |
| 5 | `challenge` | yes | Unless a valid pass token is held |
| 6 | `redirect` | yes | Runs before block: terminal buckets go gentlest first |
| 7 | `block` | yes | |

An unrecognised `response:` value falls into `block`, deliberately, so a typo cannot promote
a rule to `allow`.

### 1.3 Weight

Within a bucket, `usort` on `($a['weight'] ?? 0) <=> ($b['weight'] ?? 0)`:

- **Lower runs first.** `weight: -200` precedes `weight: 0` precedes `weight: 50`.
- Default is `0`.
- Ties break on **declaration order** — PHP's sort has been stable since 8.0, and this is
  observable:

  ```
  negative (-5)
  first (0)
  second (0)
  ```

Weight never crosses a bucket. That is the whole of what #74 is about.

## 2. The 3.0 model

### 2.1 One ordered list, first *terminal* match wins

Rules are evaluated in a single weight-ordered pass. The first rule that matches **and has a
terminal action** decides the request; non-terminal rules match, act, and evaluation
continues.

> **This is the correction to #74.** "Single pass, first match wins" was written when every
> response was terminal. Since 2.26.0, `mark` and `record` are not: they exist precisely to
> act without deciding. A literal first-match-wins pass would make the first `mark` rule
> terminate evaluation, which would silently turn marking into blocking on every config that
> uses it.

| Action | Terminal | On match |
|---|---|---|
| `allow` | yes | Serve the request; stop |
| `challenge` | yes | Serve the interstitial; stop |
| `redirect` | yes | Redirect; stop |
| `block` | yes | Refuse; stop |
| `mark` | no | Annotate; continue |
| `record` | no | Write to the block list; continue |

`response:` stops selecting *when* a rule runs and means only *what it does*. That is the
change an operator will feel.

### 2.2 Weight direction: keep lower-first (closing #38 as "no")

#38 proposes inverting it: higher number evaluated earlier.

**Recommendation: do not.** Reasons, in order of weight:

1. **It is a silent semantic inversion of a value that already exists in every config.** A
   config that is not migrated does not fail — it runs in exactly the reverse order. A rule
   set built so a narrow allow precedes a broad block would invert to a broad block
   preceding a narrow allow, and the symptom is legitimate traffic being refused, on a
   deploy that reported success. Every other 3.0 change fails loudly by comparison.
2. **It buys nothing that ordering does not already buy.** Both directions express every
   possible order. The argument for higher-first is intuition ("higher priority"), and the
   argument against is that the intuition is not shared — cron, `nice`, CSS `z-index` and
   `sort` disagree with each other about which way is up.
3. **It doubles the migration.** With lower-first retained, migration is a reordering. With
   it inverted, migration is a reordering *and* a sign flip, and a config that is partially
   migrated is silently half-inverted.

If the intuition matters, a **separate key** with the opposite sense (`priority:`, higher
first, mutually exclusive with `weight:`) costs nothing and breaks nobody. That is a 3.x
enhancement, not a 3.0 breaking change.

### 2.3 Where the durable block list goes

Today it sits between `allow` and everything else, which encodes a real policy: **an explicit
allow rule beats a ban**. That is what lets an operator unblock their office without clearing
the list.

In one ordered pass it becomes a rule with a position. Proposal: a synthetic entry at
**weight `-100`**, documented and overridable:

```yaml
global:
  block_list_weight: -100      # default
```

- A rule weighted below it beats the ban. A **migrated** config satisfies that
  automatically — §3.1 rewrites every allow rule to `-1000` and below — so today's behaviour
  is preserved without the operator choosing a number.
- A rule weighted above it does not, which is the new capability: a high-confidence block
  that should outrank a broad allow.

!!! note "This is the one number a hand-written 3.0 config has to know about"

    `-200` is the conventional allow-list weight across the shipped presets and docs today
    (`sources.md`, `user-agent.md`, `drupal-admin.yml`), and it happens to sit below `-100`.
    But `ai-crawlers.yml` uses `-50`, and under 2.x that still beats the block list because
    *every* allow rule does. Written by hand against 3.0, it would not.

    That is the model working as intended — position now means what it says — but it is a
    real trap for somebody editing a config rather than migrating one, and it belongs in the
    3.0 upgrade notes rather than being discovered.

This is the only part of the model that is genuinely new configuration rather than a
rearrangement, and it is the part most worth reviewing.

### 2.4 What does not change

The prologue (§1.1), the meaning of every `response:` value, the unrecognised-value fallback
to `block`, tie-breaking on declaration order, and the default weight of `0`.

## 3. Migration (what #224 implements)

### 3.1 The transformation

Today's order is entirely determined by (bucket, weight, declaration index). Tomorrow's is
(weight, declaration index). So preserving today's outcome is a total function:

```
new_weight(rule) = BUCKET_BASE[bucket(rule)] + rank_within_bucket(rule)
```

with bases spaced far enough apart that no two buckets can interleave:

| Bucket | Base | Note |
|---|---|---|
| `allow` | `-1000` | |
| *(durable block list)* | `-100` | `global.block_list_weight` |
| `mark` | `0` | Non-terminal; relative order preserved |
| `record` | `1000` | Non-terminal |
| `challenge` | `2000` | |
| `redirect` | `3000` | |
| `block` | `4000` | |

`rank_within_bucket` is the rule's index after today's sort, so relative order inside a
bucket survives. The result is verifiable: evaluating any request against the old config and
the new one must produce the same verdict, which is what #221 exists to check at scale and
what `firewall-check --explain` checks one request at a time.

### 3.2 What the tool must refuse to do silently

The migration preserves behaviour, and preserving behaviour is not always what the operator
wants — #74 exists because today's ordering *cannot* express some things. Two cases to
report rather than decide:

1. **A broad allow above a high-confidence block.** Preserved, the allow still wins. That is
   the exact case #74 was filed to make changeable, so the tool should name the pair and say
   so — the example in #224 is this case.
2. **A ban that an allow rule currently overrides.** After migration it still does, via
   `block_list_weight`. An operator who did not know that was happening should be told,
   because it is the difference between "this address is banned" and "this address is banned
   unless it is in the office".

### 3.3 What cannot be migrated automatically

Nothing, mechanically — which is worth stating, because #224's own example implies otherwise.
Every 2.x config has an exactly-equivalent 3.0 ordering. What cannot be *automated* is the
judgement about whether the preserved order is the order you want, which is why the output is
a file to review rather than a file to deploy.

## 3.4 The shipped presets are configs too

Every preset in `presets/` carries weights, and they are read by configs this project does
not own. 3.0 has to ship presets that are already migrated, and the migration tool has to be
able to run over a config that **includes** presets without rewriting the preset itself —
`{presets_dir}` files live in `vendor/` and are replaced on every update.

So: migrate the shipped presets in the 3.0 branch, and have the tool treat included files as
read-only, reporting the effective order rather than editing somebody's vendor directory.
This is the part of #224 most likely to be missed, because it does not show up until the
first config that includes a preset — which is most of them.

## 4. Open questions

1. **`block_list_weight` as a global, or a position in the rule list?** A global is simpler;
   a synthetic rule entry (`plugin: block_list`) is more honest about the model being one
   list. The global is proposed above because it is migratable without inventing a rule the
   operator did not write.
2. **Should `record` continue to run after a terminal match?** Today it cannot, because it
   runs before them. In one ordered pass, a `record` rule weighted after a `block` rule never
   fires. That is consistent, and it may surprise somebody who wanted "record everything that
   gets blocked" — which is what the [decision events](../docs/how-to/decision-events.md)
   are for, and worth saying in the release notes.
3. **Does `allow` still short-circuit non-terminal rules?** Today an allow match skips mark
   and record entirely. Under one ordered pass, a `mark` rule weighted *before* the allow
   would fire first. That is a behaviour change for anybody weighting a mark below an allow,
   and the migration's bucket bases above preserve the current outcome (mark base `0` is
   after allow's `-1000`).

---

## 5. Why this is in the 2.x line

The migration tool has to exist, and have been used, before the release that needs it. That
means it ships in 2.x — which means this model has to be settled while 2.x is still the
current line, even though nothing here changes 2.x behaviour.
